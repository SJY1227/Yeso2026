# 제품 설계와 개발 기준

이 프로젝트의 우선순위는 화면 수나 시연 완료보다, 변경할 때 다른 기능을 함께 고치지 않아도 되는 구조와 기록의 일관성이다. 아래 문서는 구현을 대체하는 산출물이 아니라 코드와 함께 갱신할 판단 근거다.

처음 저장소를 받았다면 [개발 환경 준비와 저장소 구성](repository.md)을 먼저 읽는다. 현재 구현 범위는 [개발 상태 v0.8.2](development.md), 실제 검사 결과는 [검증 기록](../validation.md)을 따른다.

1. [기획 근거와 미확정 사항](product-baseline.md): 어떤 내용이 확정됐고 어디서 나왔는지.
2. [시스템 설계](architecture.md): 책임, 의존 방향, 상태·시간·저장의 관계.
3. [기능과 화면의 연결](flows.md): 제품 흐름, 예외, Figma 참조.
4. [결정 기록](decisions.md): 선택 이유와 다시 검토할 조건.
5. [개발 순서](development.md): 먼저 해결해야 할 의존 관계와 실제 구현 범위.
6. [엔진 연결 계약](engine-integration.md): 실제 함수·상태·저장 확정 순서와 현재 한계.
7. [입력·절전·시간 동기화](input-power-time.md): 1개/3개 버튼 교체 지점, 매 기상 시각 동기화, Wi-Fi 최초 설정과 재접속.
8. [제품 실행 계층](product-runtime.md): 실제 버튼 흐름, 먹이·성장·도감·요약, 저장·복구, 일정 입력, 구현 용량과 후속 연결점.

9. [UX·Figma·API 대조](source-review-2026-10-03.md): 새 자료의 신뢰 범위, 서버 계약, 성장·배터리·ACK 충돌과 다음 연동 순서.

2026-10-05 현재: 보관된 개발자 Notion의 기기 API와 구현을 다시 대조했다. UUID 인증·KST 규약에 맞춘 HTTPS 어댑터·완료 회신 대조·일정 병합/보관에 이어, 동기화 중 조작 화면 보존과 전체 과거 기록 백업을 보완했다. 성장 규칙은 사용자의 Figma 우선 결정으로 단계별 40·50·60을 구현했다. 실제 서버 연결과 서버 성장 정책 조정·배터리 unknown·부분 ACK·일정 수정 계약은 남아 있다. 개별 문서의 날짜와 상충 내용을 보존하고 자료 수신을 기능 완료로 취급하지 않는다.
