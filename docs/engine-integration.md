# 루틴 엔진을 애플리케이션에 연결하는 방법

[RoutineEngine.h](../firmware/RoutineDevice/src/domain/RoutineEngine.h)는 하나의 큰 루틴 발생 회차에 대한 계산 계약이다. 아직 HTTP DTO나 저장 파일 형식은 아니다. 일정 수신기, UI 조작기, 영구 저장 어댑터를 구현할 때 이 경계를 기준으로 연결한다.

## 입력과 범위

`RunSpec`은 로컬 실행 회차 식별자, 시작·마감 절대 시각, 순서가 고정된 작은 루틴 식별자를 받는다. 이름·문구·이미지는 렌더링을 위한 별도 콘텐츠다. API ID를 숫자로 잘라 넣거나 해시 충돌을 무시하는 식으로 연결하지 않는다. 명세를 받으면 ID 표현과 매핑·보존 방법을 확정한다. 현재 `RunId`/`StepId` 숫자는 내부 불투명 키이며 서버 필드 형식을 정한 것이 아니다.

현재 구현 한도는 큰 루틴당 작은 루틴 16개다. 이는 고정 메모리로 엔진을 검증하기 위한 구현 용량이며 제품 정책이 아니다. 더 큰 입력은 명시적으로 거부한다. 명세·운영량을 확인한 뒤 `kMaxSteps`와 보상 권리 표현을 함께 검토해야 하며, UI에서 조용히 목록을 잘라서는 안 된다.

`createRun`에 마감 경계 규칙과 경고 선행 시간을 반드시 전달한다. 생성 실패는 기존 출력 상태를 변경하지 않는다. 미설정·중복된 작은 루틴 ID, 빈 목록, 잘못된 시간 구간 등을 거부한다. 경고 선행 시간이 루틴 길이보다 길면 시작 시점부터 경고 대상이 된다.

## 상태 변화

`advanceTime`은 시간이 지나 생기는 변화, `dispatch`는 화면/사용자 의도를 처리한다. 두 함수 모두 원래 상태를 수정하지 않고 `Transition`을 반환한다. 엔진은 heap, GPIO, 파일 시스템, HTTP를 사용하지 않는다.

`Transition`에는 다음 상태, 이벤트 목록, 처리 결과가 있다. `changed()`가 true이면 저장할 변화가 있다는 뜻이다. **`result == Applied`만 보고 저장 여부를 결정하면 안 된다.** 예를 들어 마감 순간의 완료 요청은 `DeadlinePassed`로 거부되지만 함께 계산된 `RunExpired`는 저장해야 한다. 잘못된 입력이 들어와도 같은 시점의 경고/시작 변화가 존재할 수 있다.

화면에는 실행 회차와 상태 버전을 함께 전달한다. 확인창을 열 당시의 버전·작은 루틴 ID로 명령을 만든다. 엔진에 보내기 직전에 버전을 최신 값으로 임의 교체하면 오래된 입력 방지 기능을 무력화하므로 금지한다.

## 애플리케이션의 확정 순서

```text
현재 확정 상태 + 요청 + 신뢰 가능한 시각
    → 엔진이 다음 상태와 이벤트를 계산
    → changed()가 false면 결과만 UI에 전달
    → changed()가 true면 다음 상태와 이벤트를 원자적으로 저장
    → 저장 성공 시 현재 상태 교체
    → 화면 모델 재생성, 필요한 알림/연출, 전송 예약
```

저장 실패 시 기존 확정 상태를 유지하고 오류를 전달한다. 쓰기 결과가 불확실할 수 있으므로 같은 부팅에서 재시도하지 않고 재시작 후 검증된 원장을 복원한다. 실제 코덱·두 스냅샷·NVS 세대 번호·읽기 검증은 [제품 실행 계층](product-runtime.md)에 연결했다.

엔진 이벤트의 내부 키는 `(run, kind, step)`이다. 회차 키는 날짜가 바뀌어도 재사용하면 안 된다. `Event`의 시간은 엔진이 그 변화를 관찰한 시각이며, 늦게 깬 경우 원래 예약 시작·마감은 `RunSpec`과 다를 수 있다. API 명세를 확인할 때 예약 시각과 관찰/신고 시각의 의미를 구분한다. 이벤트와 해당 실행 정의의 연결을 보존한다.

## 보상 권리와 보상 소비

`earnedRewards`는 **각 작은 루틴 완료로 발생한 권리의 이력**이다. “현재 보유 먹이 수”나 “아직 먹이지 않은 먹이 수”가 아니다. 현재 엔진에서는 이 비트를 지우지 않는다. 포기·만료·큰 루틴 완료 후에도 유지한다.

먹이의 선택·획득·소비·성장·진화는 엔진 위 애플리케이션과 `domain/Companion.h`에서 다룬다. v0.5의 회차별 먹이 ID·`consumedRewards`는 완료 권리를 참조하고 소비와 경험치를 같은 저장에 묶는다. 이력 비트를 꺼서 소비를 표현하거나 화면 연출 완료를 소비의 유일한 증거로 쓰지 않는다. 사용자 Figma 우선 결정으로 먹이 소비당 +1, 단계별 40·50·60을 적용한다.

## 현재 연결 상태

- PC 테스트가 순수 엔진을 직접 실행한다.
- Arduino 빌드는 엔진 소스의 ESP32 호환성을 함께 검사한다.
- 기본 실행은 ProductRuntime이며 UI·영구 저장·예약·절전 경계를 연결했다.
- 제품 애플리케이션은 Board를 재사용하고 Hardware Check와 명령 파서를 분리한다. 완료·먹이 배정, 소비·성장, 소유 선택, 하루 요약 확인을 저장과 연결했다. v0.7에서 확보한 원본/모션·운영 일정 갱신/보존·API 어댑터를 추가했다. 실제 서버 연결과 미확정 계약/일부 원본은 남아 있다.

따라서 “엔진 테스트 통과”와 “실제 사용자의 루틴을 저장하면서 수행할 수 있음”은 별개의 완료 상태다.


v0.7의 `remoteCompleted`는 서버에서 관측한 완료이며 로컬 `earnedRewards`와 분리한다. `completedMask()`/`nextStep()`으로 중간 단계만 서버 DONE인 경우를 처리하고 해당 DONE을 로컬 먹이 권리로 다시 지급하지 않는다. 서버 확인 비트는 별도의 `syncedRewards`다. 과거 회차를 활성 목록에서 정리할 때 원장 백업과 누적 먹이/성장/수집 보존은 애플리케이션이 담당한다.
