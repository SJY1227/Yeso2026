# 기획 근거와 미확정 사항

## 근거를 구분하는 방법

| 표시 | 의미 | 취급 |
|---|---|---|
| 확정 | 사용자가 직접 확인하거나 이번 기기에서 검증 | 현재 구현의 기준 |
| 자료상 흐름 | PDF 제품 설명 / Figma에서 확인 | 제품 의도로 참고. 세부 정책까지 확정된 것으로 확대하지 않음 |
| 기존 기록 | 이전 로컬 문서에 적힌 내용 | 원문과 최신 자료 대조 필요 |
| 설계 결정 | 이번 개발에서 정한 기술 선택 | 이유와 변경 조건을 기록 |
| 미확정 | 근거 부족 또는 서로 다른 자료 | 임의 기본값을 제품 규칙으로 고정하지 않음 |

사용자의 최신 설명을 우선하고, 실제 하드웨어 확인값을 예전 문서의 부품·배선 정보보다 우선한다. **2026-10-03 사용자가 'Figma를 최우선으로' 결정했으므로 성장 목표는 Figma의 단계별 40·50·60을 적용한다.** API의 통신 필드·인증은 기존 계약을 참고하되 상충하는 서버 성장 정책은 수정/조정 대상으로 기록한다. 날짜·배터리 백분율 등 화면의 다른 예시값까지 실측값이나 제품 정책으로 승격하지 않는다.

## 자료상 제품 흐름

보호자가 앱에서 큰 루틴의 시작·마감 및 작은 루틴의 순서를 정한다. 기기가 받은 일정을 보관하고, 네트워크가 없어도 안내·수행 기록을 처리한다. 작은 루틴 완료는 사용자의 신고이며 실제 행동을 센서로 자동 판정하는 기능은 제시되지 않았다.

큰 루틴 시작 → 편지 알림 → 현재 작은 루틴 표시 → 완료 재확인 → 먹이 획득·주기 → 성장 표시 → 다음 작은 루틴이라는 흐름을 확인했다. 포기는 재확인 후 큰 루틴을 종료하는 것으로 PDF에 설명돼 있다. 작은 루틴별 제한 시간이 아니라 상위 큰 루틴의 마감을 적용한다는 설명도 있다. 이 두 정책은 API와 최종 시나리오를 대조해야 한다.

먹이·캐릭터 도감, 진화·새 캐릭터, 하루 요약, 페어링·연결 오류·배터리 화면이 존재한다. 화면 존재를 곧바로 구현 가능한 센서·서버 기능의 존재로 해석하지 않는다.

| Q02 | 날짜별 big/smallRoutineId 확보; 변경 버전·부분 ACK 미확정 | API 보완 | 화면 상태와 실행 상태 분리, 임의 일정 덮어쓰기 방지 |
| Q03 | 성장·보상 데이터의 최종 관리 주체와 중복 처리 | API 명세, 최종 규칙 | 완료와 보상 권리를 한 처리 단위로 설계 |
| Q04 | 성장 목표는 40/50/60 확정. 먹이별 확률·새 캐릭터 제안 순서는 미확정 | 최종 확률/콘텐츠 규칙 | 먹이당 +1·같은 가중치·확보 콘텐츠 순 제안을 교체 가능한 구현 선택으로 분리 |
| Q05 | 겹치는 일정, 진행 중 수정·삭제, 날짜·시간대 변경 | 앱 정책·서버 계약 | 변경 충돌을 명시적 상태로 노출하는 설계 |
| Q06 | 알림 반복, 마감 경고 시점, 뒤늦게 깬 경우 | 최종 시나리오 | 시간 소스와 판단 로직 분리 |
| Q07 | Previous/Next/Confirm은 사용자 확정; 화면별 UX 변형 선택은 일부 미확정 | 디자인 조작 정의 | 1개/3개 매핑·커서·확인창·깨우기 입력 소비 구현 |
| Q08 | 기기가 보관할 일정 일수·이벤트 수·콘텐츠 크기 | API 명세·운영 조건 | 저장 예산 산정. 넘치면 명시적 오류 |
| Q09 | 실제 배터리 잔량·충전 상태 표시 방법 | 회로·측정 확인 | Unknown 상태 지원, 샘플 아이콘과 실측값 구분 |

새 자료를 받을 때 문서명·링크·수정일·관련 주제·충돌 사항을 기록한다. “최종”이라는 파일명만으로 다른 근거를 덮어쓰지 않는다.

추가 확인: 사용자는 이전 환경에서 **화면 절전까지 실제 동작했다**고 명확히 확인했다. 해당 소스와 명령·전력 측정값은 확보하지 못했지만, 화면 절전 성공 자체는 사용자 확인 사실이다. BL 미연결을 근거로 기능 불가·테스트 실패·추가 배선 필요라고 판단하지 않는다. 절전 통합 시 현재 배선에서 구현을 재현한다.
