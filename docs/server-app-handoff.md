# 서버·앱 개발자 전달 사항

갱신일: 2026-10-05, v0.8. API 근거는 2026-10-03에 열람·보관한 [기본 명세서](https://app.notion.com/p/API-3210ea4df78582849613811a1d597089)와 상세 페이지다. claim/sync 통신·응답 변환·병합 코드는 구현했다. **실서버 접속 정보와 미측정 배터리 계약이 없어 실제 왕복은 아직 검증하지 않았다.** 자세한 원문 대조는 [기존 검토 기록](source-review-2026-10-03.md)에 있다.

## 이미 확정된 제품 기준

2026-10-07 추가: 사용자가 전달한 앱 GATT 명세에 맞춰 [BLE Wi-Fi 설정](ble-wifi-provisioning.md)을 개발 빌드에 구현했다. 기기가 광고하고 Flutter 앱이 검색·연결한다. 평문 BLE와 로컬 숫자 IPv4 HTTP는 명시적인 개발 모드에서만 허용한다. 조각 누적, 3초 대기 의미, 7자리 예시 암호, Wi-Fi 변경 시 불필요한 페어링 등 앱 수정 사항을 별도 문서에 정리했다. 실제 앱·서버·실물 연동은 아직 미검증이다.

| 항목 | 펌웨어의 기준 |
|---|---|
| 성장 | 사용자의 Figma 우선 결정: **먹이 소비당 경험치 +1**, 단계 목표 **40·50·60**, 누적 **40·90·150** |
| 보상 | 작은 루틴 완료로 먹이 권리/종류를 저장. 안내 확인과 실제 먹이 소비는 별개이며 각각 중복 방지 |
| 도감 | **10종 × 3단계 = 30칸**. 종 소유와 단계 수집을 분리. `n/30`은 현재 탐색 위치 |
| 다시 키우기 | 완성한 종을 선택하면 현재 육성량은 초기화하지만 소유·최고 수집 단계는 보존 |
| 입력 | 이전/다음/확인 세 의도. 현재 D3 단일 버튼을 1회/2회/0.8초 유지로 매핑 |
| 홈 | 이전·다음은 도감 선택. 확인은 상태별 성장/요약 처리, 아무 할 일이 없으면 홈 유지. 대기 편지/먹이는 상태에 따라 우선 표시 |
| 시간 | 처음 저장한 Wi-Fi를 재사용하고 **매 절전 복귀마다 Wi-Fi/NTP 시간 동기화를 요청**. 서버 sync와 별개 |
| 저장 | 쓰기 스키마 4, 1~4 읽기. 일정/완료/먹이/성장/수집/이벤트/서버 확인을 하나의 확정 단위로 저장 |

성장 기준을 사용자에게 다시 선택받을 사안으로 남기지 않는다. 서버의 기존 수치를 제품 기준에 맞추거나, 기기/서버의 책임을 합의해 충돌을 제거해야 한다.

## 현재 확보한 HTTP 계약

[claim 상세](https://app.notion.com/p/claim-3a60ea4df78581cfb0ecf57bd5a5b5cb): `POST /device-api/v1/claim`, 인증 없음. `pairingCode`는 **숫자 10자리 문자열**로 선행 0을 보존하고 `deviceUid`, `firmware`를 함께 보낸다. 성공 시 `deviceId`와 `deviceAccessUuid`를 저장한다. 코드 10분/일회용. 404 없음·이미 사용, 410 만료, 409 다른 계정 등록. 응답 유실 복구는 별도 합의가 필요하다.

[sync 상세](https://app.notion.com/p/push-pull-3a60ea4df78581ef9befd8b993986bd7): `POST /device-api/v1/sync`, `X-Device-Uuid` 헤더. 요청의 `battery`, `firmware`, `completions`, `dates`는 필수다. 완료가 없으면 빈 배열. 각 완료는 `smallRoutineId`, `status`, `completedAt`; DONE 시각은 UTC timestamp, PENDING은 비운다. 날짜는 `yyyy-MM-dd`. 최대 3일은 문서의 제안이며 확정된 서버 상한으로 취급하지 않는다.

응답은 `success/data/error` 봉투, `serverTime`, `accepted`, 날짜별 `bigRoutines`/`smallRoutines`다. 실제 날짜별 `bigRoutineId`/`smallRoutineId`를 내부 회차 ID에 연결하며 반복 계열의 `seriesId`로 대체하지 않는다. HH:mm은 KST 날짜와 결합해 UTC로 변환한다. 자정·날짜 경계·순서·중복 ID·문자열 길이·용량 초과를 어댑터에서 검증해야 한다.

[캐릭터 상세](https://app.notion.com/p/3a60ea4df78581ad9947c65fa98bc344)의 `GET /api/v1/children/{childId}/characters`는 **앱용 X-Access-Uuid 인증**이다. 보호자 자격증명을 기기에 복사하지 않는다. 최신 검토 명세의 인증은 JWT/refresh가 아닌 UUID이며, `401 DEVICE_UNAUTHORIZED`에는 재페어링 흐름이 필요하다. 초기 세팅 문서에 남은 JWT·secret·refresh 설명은 현재 구현 근거에서 제외했다.

## 캐릭터 식별자 매핑

아래 숫자는 현재 펌웨어의 **로컬 저장 ID**이며 서버 code로 확정한 값이 아니다. 서버 ID 매핑표를 따로 받는다. 0과 1은 기존 사용자 기록이 있어 순서를 바꾸지 않는다.

| 로컬 ID | 종 / 현재 이름 | 단계 |
|---|---|---|
| 0 | 양 / 몽실이 | 1·2·3 |
| 1 | 빨강 로봇 / 또비 | 1·2·3 |
| 2 | 뿔 캐릭터 / 메에 | 1·2·3 |
| 3 | 초록 로봇 / 저스티스 | 1·2·3 |
| 4 | 고양이 / 냐요미 | 1·2·3 |
| 5 | 강아지 / 맘뭉이 | 1·2·3 |
| 6 | 물범 / 정식 이름 확인 중 | 1·2·3 |
| 7 | 파랑 로봇 / 정식 이름 확인 중 | 1·2·3 |
| 8 | 곰 / 북극곰 | 1·2·3 |
| 9 | 토끼 / 깡충이 | 1·2·3 |

도감의 페이지 번호는 현재 육성 종부터 순환하므로 영속 ID가 아니다. `종 ID + 단계`로 저장·전송해야 한다. 기존 스냅샷의 50칸 예약 공간은 호환성을 위해 유지하되 실제 콘텐츠는 10종이다. 50종을 구현했다는 뜻이 아니다. 테마·이미지는 상태 원장과 분리된 버전 파일이며 교체해도 소유/XP를 초기화하지 않는다.

## 현재 구현 한도와 연결 순서

활성 큰 루틴 **16개 × 작은 루틴 최대 16개**, 이벤트 1,024개, 문자열 UTF-8 95바이트, 스냅샷 64KiB다. sync 한 번은 최대 3날짜/64완료, 응답 96KiB·중첩 10·JSON 할당 256KiB다. 서버 상한이 아니라 기기의 방어 한도이며, 초과 응답 일부만 반영하지 않는다.

진행 전 미래 일정은 갱신 가능하고 진행 중 구조 변경은 충돌로 보류한다. 응답에서 빠졌다는 이유로 삭제하지 않는다. 서버 DONE은 완료 상태에 합치되 로컬 먹이를 다시 주지 않는다. `accepted` 개수만으로 ACK하지 않고 **이번 요청에 실은 회차/단계/완료 시각과 응답 DONE이 정확히 일치**할 때만 확인 처리한다. 서버가 시각을 바꾸거나 반올림하면 확인되지 않은 기록으로 남으므로 계약 확인이 필요하다.

과거 회차는 종료·결과 확인·로컬 먹이 전량 소비·로컬 완료 전량 확인 조건을 모두 충족해야 정리한다. 먼저 `history-<generation>.bin`을 영속 기록하고, 누적 먹이 획득량·경험치·수집 단계와 정리 경계를 함께 저장한다. 어제와 오늘은 활성 목록에 유지한다. 160일 진행·진화·재부팅·정리는 PC에서 검증했으며 장기 실물 사용을 뜻하지 않는다. 백업 파일이 차면 기록을 지우지 않고 정리를 보류한다.

통신은 별도 FreeRTOS 작업에서 TLS 인증서를 검증한다. 검증 생략/리디렉션은 사용하지 않는다. 평상시 5분, 상태 변경 후 최소 2초, 기상 시 전송을 예약하고 일시 오류는 10~300초 간격으로 재시도한다. 401·다른 영구 거절·잘못된 응답·병합 충돌은 보류한다. claim 전 불확정 상태를 저장하고 응답 유실 때 일회용 코드를 자동 재사용하지 않는다. 등록 성공 조회 계약이 없으므로 이 경우 자동 복구는 미구현이다.

설정은 `tools/configure-api.ps1 -Port COM5 -BaseUrl <https origin> -RootCaPath <PEM>`을 사용한다. 선택적 `-Pair`는 코드를 숨겨 입력받는다. Wi-Fi는 `configure-wifi.ps1`, 상태는 `api status`, 전송 예약은 `api sync`, 진행 백업은 `backup-state.ps1`이다. 설정·UUID·Wi-Fi 암호는 진행 백업에 포함하지 않는다.

[XIAO ESP32-S3 Plus 공식 회로도](https://files.seeedstudio.com/wiki/SeeedStudio-XIAO-ESP32S3/res/XIAO_ESP32S3_Plus_V1.1_SCH_260115.pdf)를 대조했다. GPIO10의 ADC_BAT는 확장 커넥터 신호이며 현재 배선에 VBAT 분압 측정 회로는 없다. 부동 ADC를 배터리 %로 보내지 않는다. 서버에서 unknown을 허용하거나 별도 측정 회로·보정 기준이 제공돼야 실제 sync를 활성화할 수 있다.

현재 HH:mm 종료가 시작 이하인 자정 넘김 일정과 활성 실행 구간 겹침은 거절한다. 서버가 이를 허용한다면 제품 정책을 먼저 맞춰야 한다. 작은 루틴 ID는 현재 내부 uint32 범위이며 그보다 큰 ID도 거절한다.

1. 접속 정보·페어링 복구·앱 초기 Wi-Fi 전달 계약을 확정한다.
2. 구현한 DTO 변환·응답 검증을 실제 서버 성공/실패 응답과 대조한다.
3. 구현한 완료 회신 대조·재시도·일정 갱신에 대해 서버의 시각/삭제/부분 성공 계약을 확정한다.
4. 성장·선택·최고 수집 단계 조정 및 기기용 상태 수신을 연결한다.
5. 중복 DONE, 응답 유실, 부분 성공, 기기 재부팅, 오프라인 소비 후 재접속, 앱 일정 삭제, 자정, 재육성 후 도감 보존을 양쪽에서 검증한다.

이 문서는 전달용 초안이며 다른 개발자에게 자동으로 전송하지 않았다. 디자인 자산·이름·레이아웃 확인 사항은 [디자이너 전달 문서](designer-handoff.md)에 별도로 정리했다.


## v0.8 재검토 결과

완료 ACK/내일 일정만 갱신되는 경우 사용자가 보고 있던 도감 선택·확인창을 유지한다. 실제 현재 단계의 서버 DONE은 기존 확인창을 무효화한다. 활성 일정의 시간 구간은 USB와 동일하게 마감 포함 정책을 적용하므로 `AllowAtDeadline`일 때 이전 종료=다음 시작도 겹침이다.

HTTP/설정은 JSON 객체 뒤의 추가 문서/데이터와 NUL을 거절하며 UUID·날짜·시각·상태 문자열의 길이를 검사한다. claim 성공 결과가 아직 영속 저장되지 않았거나 응답 결과가 불확정인 상태에서는 서버 주소 변경을 막는다. 작업 생성 자체가 실패했으면 요청을 보내지 않은 상태로 처리하고, 그 사실의 저장 확인이 성공한 경우에만 사용하지 않은 코드를 재시도한다. 초과 크기 응답과 중간 전송 실패도 구별한다. 이 경로는 코드/컴파일 검증이며 실제 서버 왕복은 여전히 미검증이다.

보관된 sync 원문은 serverTime으로 RTC를 보정한다고 적혀 있다. 현재 기기는 사용자 요청대로 매 기상 NTP 동기화를 호출하며 **serverTime을 시스템 시계에 직접 설정하지 않는다**. 응답 필드 검증/완료 상태 비교에 사용한다. 두 시각 소스의 허용 차이와 최종 권위는 서버 연동 시 확인 대상이다.

전체 진행/과거 기록 내보내기는 `tools/backup-state.ps1 -Port COM5 -All`이다. SHA-256 영수증을 함께 만들고 원래 과거 파일은 기기에 보존한다. 이미 있는 PC 파일은 해시가 같으면 재사용하고 다르면 덮어쓰지 않는다. 백업이 기기 공간 정리나 앱으로의 성장 동기화를 대신하지 않는다.
